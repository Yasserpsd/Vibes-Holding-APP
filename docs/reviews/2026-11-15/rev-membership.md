### Round 3 — defects the Android emulator run found (`rev-android-run.md` items 5, 11, 21, 37)

- **Item 5 — riyal symbol on top of the last digit** — `components/SarText.tsx:19-25,30-56`. Cause (read in `node_modules/react-native/ReactAndroid/.../views/text/TextLayoutManager.kt`, the «TODO(5578671): Handle text direction» above `createLayoutForMeasurement`, and `getParagraphDirection` at the attachment position): a price that is ONLY a number and the symbol («30,000 ريال», «15,000 ريال», «1,500 ريال») has no letter to give the line a direction. The Android `TextView` then draws it by the screen's direction (right-to-left: the gap kept for the symbol is on the LEFT of the number), while React Native measures where to put the inline image with a left-to-right default (the far RIGHT end) — so the symbol lands on the last digit. Font size and the strike-through are not the cause: «950» / «450» have an Arabic label in the same string and «13,500» has the LRM that `MonthlyDeal` adds, which is why they were fine. Fix: when the text around the symbol has no letter and no direction mark, `SarText` puts one invisible mark in front — RLM in Arabic, LRM in English — so both sides agree; text that already has a letter or a mark is untouched. One fix for every call site: the service list price, struck price and «المبلغ» (`service/[key].tsx:175-176,314`), the struck event price (`agenda/[id].tsx:177`, `WorkshopAd.tsx:115`), and the same number-only prices in my own screens that the run did not reach (`checkout/[id].tsx` amount, `payments/index.tsx`, `payment/[id].tsx` amount row, the store price in `StorePurchaseCard.tsx` and `MembershipGate.tsx`) plus `requests/index.tsx` and `affiliate/index.tsx`.
- **Item 11 — status badges unreadable in the light theme** — `components/MembershipStatusCard.tsx:86-89`. The badge is a solid status tone with the fixed dark `goldInk` on it; the light theme's tones are deep (`success #177A53`, `warning #8F6A12`). The ink is now `colors.black`, the page colour of each theme (near-black in dark, near-white in light) — the status tones are designed to contrast with exactly that colour. Contrast, badge text on its tone: light «عضو» 4.9:1, «غير مفعّلة» 4.6:1, «منتهية» 4.5:1, «زائر» 4.7:1; dark all ≥ 5:1 (the look in the dark theme is unchanged).
- **Item 21 — «Investors Club» twice on the member card** — `app/card.tsx:122-126`. The spaced-capitals line is removed (and its style); the name line stays. «Promo Code» and «Membership No.» are untouched.

### Round 4 — «اشتريت العضوية ولازم أقفل التطبيق وأفتحه عشان تتفعّل» (2026-11-16)

Source: `docs/reviews/2026-11-16/complaint-membership-needs-restart.json` (`challenge.finalFixPlan` priorities 1, 2, 3, 4, 5, 8, 10 — the OTA items — plus the missed cause about `/membership`). JavaScript only. Rule 5 holds everywhere: the only thing that ever changes the membership in the app is an account the SERVER returned (`adopt()`); the store's answer, the saved flag and the timers only decide when to ASK.

1. **One door for the account, one reaction to a change** — `auth/AuthProvider.tsx:99-122`. Every account answer (launch, `refresh()`, a profile update, a membership check) goes through `adopt()`. When the same account's status / kind / end date differs from the copy the app held, `queryClient.invalidateQueries()` runs once (wallet card, event prices, services, people, affiliate, persisted copies). The saved copy of a launch and a new session only set the baseline; an identical answer keeps the same object (no re-render storm now that the app asks more often). Each read takes a number when it starts and an answer older than one already applied is dropped, so a slow, stale «not a member» can never overwrite a newer «active»; answers arriving after a sign-out are dropped too.
   **Back to the app** — on every return to the foreground a signed-in account that is not a confirmed, active member is re-read. Since round 5 this is the NORMAL read (the server's 60-second account cache stays in front of the hub), at most once every five minutes; only a watched purchase asks the fresh way, through its own check. This replaces the old listener that ran only when there was no account at all.
2. **«pending» is not sticky** — `components/StorePurchaseCard.tsx:179` (`shown`) and `components/MembershipGate.tsx:87-92` (`view`): the moment the account is active the waiting states («جارٍ التفعيل», «سيتم التفعيل خلال دقائق», the store-pending notice) give way to the success notice on the same screen — derived at render, no effect to miss.
3. **The watcher after a purchase** — flag: `lib/purchases.ts:136-176` (`savePurchaseWatch` / `loadPurchaseWatch` / `clearPurchaseWatch`, `{contactId, at}` through `deviceStore`'s guarded `saveSetting` — `deviceStore.ts` itself needed no change); loop: `auth/AuthProvider.tsx:302-364`. Started by the card and the popup the moment the store takes the payment, holds it as pending, or a restore finds the entitlement (`watchMembership()`), so it is saved BEFORE the first check. While it is set and the account is not active the app calls `/api/membership/sync`: at launch, on every return to the foreground, every 15 s for 5 minutes then every 60 s up to 30 minutes. It ends when the server answers active (`adopt()` clears it), on sign-out, or after 72 hours. While it is set, the card and the popup show the calm waiting notice with «استعادة المشتريات» instead of a second Subscribe button (`StorePurchaseCard.tsx:99-104`, `MembershipGate.tsx:90`).
4. **The popup never traps; a late answer is applied** — `components/MembershipGate.tsx:54,93,129-151,271`: after 10 s of «جارٍ التفعيل» a `common.close` button appears and Android back works; the check and the watcher go on behind the closed popup, and re-opening the popup does not reset a purchase in hand (`:98`). `syncMembership()` (`AuthProvider.tsx:284-300`) releases the caller after 8 s but keeps the request: its answer is applied whenever it arrives (the old `syncMembershipOnce` race dropped it). No new string.
5. **Tap on «تم تفعيل عضويتك»** — `components/PushRegistrar.tsx:45-58`: the account is re-read before the screen opens (4 s at most, a slower answer still updates the screen), also for the tap that launched the app. **Affiliate pushes** — `:78-79`: a push whose type starts with `affiliate` invalidates `['affiliate']`.
